# Building the Lovable app: setup and prompts (v2)

v2 adds the USP: **an assessment that learns**. The team enters an experiment result, the range moves, the verdict can flip, and the next experiment re-ranks. The field details are in [../CONTRACT.md](../CONTRACT.md).

## 1. Setup (or update from v1)

Copy the four files from `lovable/src/lib/` into the Lovable repo's `src/lib/`, either with GitHub's **Add file → Upload files** or with git, and push. Overwrite the v1 copies.

| File | What it is | Who changes it |
|---|---|---|
| `contract.ts` | TypeScript types for everything the API sends and accepts | generated by Dev B, never edit |
| `fixtures.ts` | the 5 demo runs, typed | generated by Dev B, never edit |
| `api.ts` | `api.createRun / getRun / approve / addResult / resetDemo / latestEvals` | already points at the live backend |
| `ledger.ts` | screen choice, `{{id}}` tokens, number formats, learning-loop helpers | Dev B |

`api.ts` now talks to the live backend (`USE_FIXTURES = false`). The demo runs are served live too, so `/runs/demo-success` works straight away. Set `USE_FIXTURES = true` only if the backend is down.

## 2. Working rules

- Send one prompt at a time. Test with the check under it, then bookmark the version.
- Never ask Lovable to "improve" a screen that already works. If Lovable edits `contract.ts`, `fixtures.ts` or `ledger.ts`, revert that change.
- Demo URLs: `/runs/demo-gate1`, `/runs/demo-success`, `/runs/demo-updated`, `/runs/demo-needs-input`, `/runs/demo-refused`.
- To start the demo again, call `api.resetDemo()`. A small "Reset demo" link in the footer is enough.

## 3. If you already built P1–P8 on v1

Paste this once:
> The backend contract changed to v2 (src/lib/contract.ts and src/lib/api.ts were replaced). `api.approve` now returns the full RunState, so use it to update the page instead of re-fetching. Experiments have a `rule` object; their `pass_threshold` and `kill_criterion` are read-only text. A Gate 2 edit sends `rule` instead of the two texts. ## 4. Prompts, in order

P1–P7 are unchanged from v1. They are repeated briefly here for a fresh start.

### P1 · App shell
> This app is "Lab to Market": it turns a technical idea into an honest commercial assessment in which every statement is labelled Fact, Estimate or Assumption, then learns from experiment results. src/lib/contract.ts, fixtures.ts, api.ts and ledger.ts come from the backend team: import from them and never modify them. Routes: `/` (Intake), `/runs/:id` (Run page), `/evidence` (Evidence). The Run page loads `api.getRun(id)` and picks the screen with `screenFor(run.status)` from ledger.ts; while `isWorking(run.status)` re-fetch every 3 seconds. Top bar with the app name, "New idea" and "Evidence". Calm design: white background, slate text, one teal accent.

### P2 · Claim badge and drawer
> ClaimBadge for a `Claim`. Fact: solid green, CheckCircle icon, "Fact". Estimate: blue with diagonal stripes, Calculator icon, "Estimate". Assumption: amber outline, HelpCircle icon, "Assumption". Colour, icon and text must all differ. Extra small tags: origin "user" → grey "User-supplied"; origin "experiment" → purple "Team result", and if claim.text contains "MOCKED" a red "MOCKED" tag.
> ClaimDrawer (shadcn Sheet) for a RunState plus claim id. Show the text, badge, `formatClaimValue(claim)`, evidence_strength as a 0–100% bar, sensitivity if set, and note in a callout.
> - Fact: the source title linked to its url, credibility_tier and fetched_at, the quote as a blockquote, and the line "A verified quote shows the page said this, not that it is true."
> - Estimate: derivation.formula in monospace, with the input claims as clickable badges.

### P3 · Intake
> Intake page at `/` with:
> - A large idea textarea (max 1,500 words, with a word count).
> - Optional Sector, Region and TRL (1–9) fields.
> - A scope box: "We assess technical ideas that have identifiable business customers. We ask for more detail when an idea is too vague, and refuse ideas whose main use is harm or surveillance."
> - A warning: "Your text is sent to an AI model and a web-search provider. Do not paste confidential IP."
> - A Start button that calls `api.createRun({ idea_text, context })` and navigates to `/runs/{run_id}`. Show ApiError.detail in a toast.

### P4 · Progress
> For the "progress" screen, show a vertical StageTimeline from state.steps: spinner for running, check for done, red X for failed, grey for skipped. Show each step's message and how long it took. Next to it, list state.sources with a credibility_tier tag and a "fetch failed" tag when fetch_ok is false. Also show the timeline in a collapsed "How this was made" section on the assessment screen.

### P5 · Gate 1, needs-input, refused
> Screen "gate1" edits run.interpretation, under the header "Check our reading of your idea before we research it".
> - Editable fields: summary, technology, TRL, and target_customers and market_drivers as chip lists.
> - Each assumption shows its text and its range (p10 / p50 / p90 with the unit; shares as %). All of these are editable.
> - Only assumptions without a driver have an "included" checkbox.
> - "Approve and research" → `api.approve(id, { gate: 1, approved: true, interpretation })`.
> - "Send back" with a note → `api.approve(id, { gate: 1, approved: false, note })`.
>
> Screen "needs_input" shows the reasons and an answer box per clarifying question. "Start again with answers" creates a new run with the answers appended to the idea.
>
> Screen "refused" shows a RefusalCard with a shield icon. The title depends on refusal_kind: harmful_or_dual_use "We won't assess this idea", physically_infeasible "This doesn't look physically feasible", outside_scope "Outside what we assess". Under it, the reasons and a link back to Intake.

### P6 · Assessment: report and charts
> Screen "assessment", from top to bottom:
> 1. A LimitationsBanner with assessment.limitations.
> 2. The headline, or a yellow "Insufficient evidence" panel with data_needed.
> 3. The report sections, rendered with `splitClaimRefs`. Each claim token shows `formatClaimValue` plus a small badge and opens the drawer.
> 4. A RangeBar for the output claim (market_model.output_claim_id).
> 5. A Recharts horizontal TornadoChart from market_model.tornado, using `formatAmount(n, "EUR per year")`.
> 6. A "Top-down cross-check" card when top_down_check exists.
> 7. "What we could not determine" (cannot_determine).

### P7 · Ledger table
> A claim-ledger table on the assessment screen with columns badge, text, `formatClaimValue`, evidence bar and sensitivity. Add filter chips Fact / Estimate / Assumption and a search box. Default sort is sensitivity, highest first. Clicking a row opens the drawer.

### P8 · Experiments and Gate 2 (v2)
> An Experiments section with one card per experiment, sorted by `rank` (unranked last). Each card shows:
> - `METHOD_LABEL[method]` and the hypothesis, and the metric
> - a "Rule fixed in advance" box: pass_threshold in green and kill_criterion in red
> - effort days and cost in €
> - "Tests" with the ClaimBadge of assumption_id
> - a rank badge "Run next" for rank 1, and "Chance to change the verdict: {formatPercent(decision_flip_prob)}"
>
> While run.status is "awaiting_gate2":
> - Each card has Accept, Edit and Reject. Edit lets the user change hypothesis, metric and the rule numbers (trials, pass_at_least, fail_below, and on_fail pivot or kill).
> - A field "Viability threshold (€ per year)" is prefilled from assessment.decision.viability_threshold.
> - "Approve plan and lock rules" is enabled when every card has a decision. It sends `api.approve(id, { gate: 2, approved: true, viability_threshold, decisions })`; an edit sends only the changed fields plus `rule` if it changed. Show the returned RunState.
>
> After approval, show a lock icon with "Rules locked at {locked_at}".

Check: approve on `/runs/demo-success`. The status becomes done and the cards show the lock.

### P9 · Verdict banner (new)
> At the top of the assessment screen, a VerdictBanner from run.assessment.decision:
> - A large verdict word from `VERDICT_LABEL` with a colour per verdict: continue green, pivot amber, kill red.
> - A grey "Provisional" pill when decision.provisional is true.
> - "Chance of reaching {formatAmount(viability_threshold, 'EUR per year')} a year: {formatPercent(p_viable)}".
> - The decision.reasons as a short list.
> - Small grey text: "Decided by code from rules fixed in advance, not by the AI."

### P10 · Enter a result (new)
> On each experiment card where `canEnterResults(state, experiment)` is true, add a compact ResultForm with:
> - "Yes" count (successes) and "Asked" count (trials), defaulting to the rule's trials
> - a checkbox "This is a mocked demo value", ticked by default
> - an optional note
>
> Submit calls `api.addResult(runId, { experiment_id, successes, trials, mocked, note })` and replaces the page state with the returned RunState. Validate that successes ≤ trials. Show the card's outcome as a pill (pending grey, pass green, fail red, inconclusive amber) and "{successes} of {trials_done} so far".

Check: on `/runs/demo-success` after P8, enter 2 of 10 on x1. The verdict changes to Pivot.

### P11 · Before/after panel and learning timeline (new)
> When state.updates is not empty, show a "What just changed" panel for `latestUpdate(state)` with four before → after rows, each with an arrow, the "after" value in bold, and red or green by direction:
> - the tested share: `formatBelief(prior)` → `formatBelief(posterior)`
> - revenue: `formatOutputRange(output_before)` → `formatOutputRange(output_after)`
> - chance of reaching the threshold: p_viable_before → p_viable_after as %
> - verdict: verdict_before → verdict_after
>
> Under the rows, add "Next experiment" (the first id of rank_after, with its method label) and a "MOCKED" tag when mocked is true.
>
> Below the panel, a vertical "Learning timeline" with one entry per update, oldest first: "Prior {formatBelief(prior)} → evidence {successes} of {trials} → posterior {formatBelief(posterior)}", the outcome pill, and the verdict change. Clicking an entry opens the drawer for its claim_id.

Check: `/runs/demo-updated` shows 50% → 34%, verdict Continue → Pivot.

### P12 · Evidence page
> `/evidence` loads `api.latestEvals()`. Show a table with case_id, system (pipeline or baseline), a pass/fail/info pill from `passed` (null = info), notes and metrics. Group rows by case_id so pipeline and baseline sit side by side. Above the table, show the number of checks passed and the note "Prototype evidence on a small number of cases, not statistical proof. Baseline = one unassisted prompt to the same model." If there are no baseline rows, show "Baseline not run yet".

## 5. Demo click path (for rehearsal)

1. On `/`, paste the unseen idea, then Start. Progress runs, then Gate 1: approve.
2. On the assessment, the verdict banner reads Continue · Provisional. Show the tornado, the ledger, and the three experiments with their locked rules. Approve the plan.
3. On the top-ranked card, enter a mocked bad result, e.g. 2 of 10. The before/after panel shows the range moving, the verdict flipping and the next experiment re-ranked.
