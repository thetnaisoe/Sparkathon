# Building the Lovable app: setup and prompts

You can build every screen today against the demo data, before the backend is live. The field details are in [../CONTRACT.md](../CONTRACT.md).

## 1. Setup (15 min)

1. Create the Lovable project. Connect GitHub (Settings → GitHub). Lovable creates its own repo and syncs both ways with its `main` branch.
2. Copy the four files from this folder into **that** repo under `src/lib/`, then push:
   ```bash
   git clone <your-lovable-repo-url> l2m-ui && cd l2m-ui
   cp ../Sparkathon/lovable/src/lib/*.ts src/lib/
   git add src/lib && git commit -m "Add backend contract" && git push
   ```
   Lovable picks the files up within seconds.

| File | What it is | Who changes it |
|---|---|---|
| `contract.ts` | TypeScript types for everything the API sends and accepts | generated by Dev B, never edit |
| `fixtures.ts` | the 4 demo runs, typed | generated by Dev B, never edit |
| `api.ts` | `api.createRun / getRun / approve / latestEvals` | you change only `API_BASE_URL` and `USE_FIXTURES` |
| `ledger.ts` | `screenFor`, `splitClaimRefs`, `formatClaimValue`, `METHOD_LABEL` | Dev B |

When Dev B changes the contract, they send new copies of these files. Overwrite them and push.

## 2. Working rules

- Send one prompt at a time. Test with the check under it, then bookmark the version.
- Never ask Lovable to "improve" a screen that already works.
- If Lovable edits anything in `src/lib/` except `api.ts`'s two constants, revert that change.
- Demo URLs: `/runs/demo-gate1`, `/runs/demo-success`, `/runs/demo-needs-input`, `/runs/demo-refused`.

## 3. Prompts (copy-paste in order)

### P1 · App shell
> This app is "Lab to Market": it turns a technical idea into an honest commercial assessment in which every statement is labelled Fact, Estimate or Assumption. The files src/lib/contract.ts, src/lib/fixtures.ts, src/lib/api.ts and src/lib/ledger.ts come from the backend team: import from them and never modify them. Set up routes: `/` (Intake), `/runs/:id` (Run page), `/evidence` (Evidence). The Run page loads `api.getRun(id)` and chooses what to show with `screenFor(run.status)` from ledger.ts. For now, show a placeholder card per screen that displays the screen name and run.status. Add a top bar with the app name and links "New idea" and "Evidence". Calm design: white background, slate text, one teal accent colour.

Check: each demo URL shows a different placeholder.

### P2 · Claim badge and drawer
> Create a ClaimBadge component for a `Claim` from contract.ts. Fact: solid green with a CheckCircle icon and the label "Fact". Estimate: blue with diagonal stripes, a Calculator icon and "Estimate". Assumption: amber outline with a HelpCircle icon and "Assumption". Colour, icon and text must all differ so the badges work for colour-blind users. If claim.origin is "user", add a small grey "User-supplied" tag.
> Create a ClaimDrawer (shadcn Sheet) that takes a RunState and a claim id. Show claim.text, the badge, `formatClaimValue(claim)`, evidence_strength as a 0–100% bar, sensitivity if not null, and claim.note in a callout if set.
> - For a fact, show its source (the entry in state.sources whose id is claim.source_id): the title linked to the url, credibility_tier as a tag, and fetched_at. Show claim.quote as a highlighted blockquote, with the line "A verified quote shows the page said this, not that it is true."
> - For an estimate, show derivation.formula in monospace and list derivation.input_claim_ids as clickable ClaimBadges that switch the drawer to that claim.

Check: on demo-success (temporarily list all claims on the placeholder), open c1 (fact), c5 (estimate), c10 (user-supplied) and c12 (demoted).

### P3 · Intake
> Build the Intake page at `/`. It has a large textarea for the technical idea (max 1,500 words, with a live word count) and optional fields Sector, Region and TRL (select 1–9). Above it, show a scope box: "We assess technical ideas that have identifiable business customers. We ask for more detail when an idea is too vague, and we refuse ideas whose main use is harm or surveillance." Under the textarea, show the warning: "Your text is sent to an AI model and a web-search provider. Do not paste confidential IP." The Start button calls `api.createRun({ idea_text, context: { sector, region, trl } })` and navigates to `/runs/{run_id}`. Show an ApiError message in a toast.

Check: Start takes you to the Gate 1 placeholder.

### P4 · Progress
> For the "progress" screen, show a vertical StageTimeline with the stages scoping, researching, verifying, modelling, ranking, experiments and composing, built from state.steps. Use a spinner for running, a check for done, a red X for failed and grey for skipped. Show each step's message and how long it took. Beside the timeline, list state.sources: title (or domain if there is no title), a credibility_tier tag, and a red "fetch failed" tag when fetch_ok is false. While `isWorking(run.status)` from ledger.ts is true, re-fetch `api.getRun` every 3 seconds. Also reuse the StageTimeline in a collapsed "How this was made" section on the assessment screen.

Check: demo-success's "How this was made" lists 7 done steps; s4 shows "fetch failed".

### P5 · Gate 1, needs-input, refused
> Screen "gate1": a review of run.interpretation headed "Check our reading of your idea before we research it." Make these editable: summary (textarea), technology, trl_guess (1–9), target_customers and market_drivers (editable chip lists), and the assumptions list, where each assumption has an `included` checkbox and inline-editable text. Add two buttons:
> - "Approve and research" calls `api.approve(id, { gate: 1, approved: true, interpretation })` with the edited interpretation, then reloads the run.
> - "Send back" asks for a short note, then calls `api.approve(id, { gate: 1, approved: false, note })`.
>
> Screen "needs_input": show run.scope.reasons, then each item of run.scope.clarifying_questions with an answer box. "Start again with answers" creates a new run whose idea_text is the original idea_text plus every question and answer, then navigates to it.
>
> Screen "refused": a RefusalCard with a shield icon. The title depends on run.scope.refusal_kind:
> - harmful_or_dual_use → "We won't assess this idea"
> - physically_infeasible → "This doesn't look physically feasible"
> - outside_scope → "Outside what we assess"
>
> Below the title, list run.scope.reasons and add a link back to Intake.

Check: demo-gate1, demo-needs-input and demo-refused.

### P6 · Assessment: report and charts
> Screen "assessment" (uses run.assessment). From top to bottom:
> 1. A LimitationsBanner listing assessment.limitations.
> 2. If evidence_floor_met is true, the headline. Otherwise a yellow "Insufficient evidence" panel that lists data_needed and says all ranges are assumption-based.
> 3. The report sections. Render the headline and each section body with `splitClaimRefs` from ledger.ts. Each claim part shows `formatClaimValue(claim)` plus a small ClaimBadge and opens the ClaimDrawer when clicked.
> 4. A RangeBar for the output claim (the claim whose id is market_model.output_claim_id): a horizontal P10–P90 bar with a P50 marker and labels.
> 5. A TornadoChart (Recharts horizontal bars) from market_model.tornado, which is already sorted. Draw one bar per driver from low_output to high_output, labelled with that claim's text and formatted with `formatAmount(n, outputClaim.unit)`. Clicking a bar opens the drawer.
> 6. If market_model.top_down_check exists, a card "Top-down cross-check" showing "{ratio}× the bottom-up market" and the note.
> 7. A "What we could not determine" panel (cannot_determine) and a "Skeptic's notes" panel (critic_notes).

Check: on demo-success, the headline reads "€240K (€70K–€820K) per year" and the tornado's top bar is achievable share.

### P7 · Assessment: ledger table
> Add a claim-ledger table to the assessment screen listing all state.claims. Columns: ClaimBadge, text, value (`formatClaimValue`), evidence strength (small bar), sensitivity. Add filter chips Fact / Estimate / Assumption and a search box. Sort by sensitivity, highest first, by default. Clicking a row opens the ClaimDrawer.

### P8 · Experiments (Gate 2)
> Add an Experiments section to the assessment screen with one ExperimentCard per state.experiments, sorted by priority. Each card shows:
> - a title from `METHOD_LABEL[method]` and the hypothesis
> - metric, pass threshold (green), kill criterion (red), effort in days and cost in €
> - "Tests assumption" with the ClaimBadge of assumption_id, and "Would update" with the badges of updates_claim_ids
>
> Each card has Accept, Edit and Reject. Edit opens inline fields for hypothesis, metric, pass_threshold and kill_criterion. The "Approve plan" button is enabled once every card has a decision. It sends `api.approve(id, { gate: 2, approved: true, decisions })`, where an edit decision includes only the fields that changed. When run.status is "done", show the plan as approved, read-only.

Check: approving on demo-success shows a success toast.

### P9 · Evidence page (Stage 5, Friday)
Wait until Dev B has eval data. The prompt will come with a sample.

## 4. Going live

When Dev B sends the backend URL:
> In src/lib/api.ts set API_BASE_URL to "<url>" and USE_FIXTURES to false. Change nothing else.

The demo runs still load from the live backend, so all the checks above should pass unchanged. Supabase Realtime comes in Stage 2: the prompt will come with the table names and filters.
